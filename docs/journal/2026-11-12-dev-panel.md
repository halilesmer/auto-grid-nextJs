# Dev panel for the local dev server

## Request
The project owner wants a small page that starts, stops and restarts the dev server on the Mac, shows its log and shows the code state. A Chrome toolbar button must open the page. The settings menu of the app has a row "open dev panel" (`SYS-15`). It opens the panel address.

## Solution
The panel is outside the repository. It is a Node program without dependencies, in the home folder of the owner. A second LaunchAgent starts it at login and starts it again after a crash. It listens on `127.0.0.1`, port `3030`, not on all interfaces. A Chrome extension (Manifest V3, loaded by hand as an unpacked extension) opens the panel tab, or brings an open tab to the front.

| Part | What it does |
|---|---|
| Status | Does the dev server answer on port `3000`, state of its LaunchAgent, version from `VERSION` |
| Start, stop, restart | `launchctl bootstrap`, `bootout`, `kickstart -k` for the LaunchAgent of the dev server |
| Log | Last lines of the log file of the dev server |
| Code state | Branch, clean or dirty tree, commits behind or ahead of `origin/main` |
| Update | `git pull --ff-only` only. It refuses unless the branch is `main` and the tree is clean |

Other git commands (push, reset, checkout, merge) do not exist in the panel. The panel never uses `sudo`.

## Why
- **Outside the repository.** The panel changes the Mac only. The repository stays free of machine paths, and the panel needs no review for each change of the Mac setup.
- **Guard.** A web site in the browser can send a request to a local port (CSRF, DNS rebinding). The panel runs `launchctl` and `git`, so each request passes these checks: the TCP peer is a loopback address; `Host` is exactly the panel address; an action is a `POST` with `Origin` equal to the panel address and a random token of the process (the page carries the token, header `x-panel-token`); an unknown action gives `404`. The status and log reads need the same token, and a browser request with `Sec-Fetch-Site` other than `same-origin` or `none` is refused. Commands use `execFile` with an argument list, not a shell string. Git runs with repository hooks and `fsmonitor` off, without optional locks and without prompts. Update takes the SHA of `origin/main` after the fetch and fast-forwards to that SHA, so the commit that the check saw is the commit that arrives. Reason for the check of the TCP peer: the guard of the VPS route in the app trusted only `Host` and `Origin` (journal entry 1107-A8), and a LAN client got through with forged headers.
- **Update only fast-forward.** A merge or a reset can lose work in the main checkout. `--ff-only` fails instead.
- **Rejected:** a route in the Next.js app. It dies together with the server that it must restart.

## Verification
- A review pass found no remote bypass and five local points (status read without token, repository hooks, git lock, pull race, status load). All five are fixed.
- 17 Node tests (`node --test`): forged `Host`, forged `Origin`, `Origin` different from `Host`, no token, wrong token, `GET` on an action, unknown action, peer that is not loopback: all refused. Status and log without token, and cross-site requests, are refused. Update refuses with a dirty tree and outside `main`. It pulls fast-forward only, and it fails with a diverged branch without a merge.
- Live: the panel answers on the port; status, log and code state show in the browser. One restart through the panel: the dev server answered again after about 7 seconds. "Update" on an up-to-date tree gave "already up to date".
- Settings menu row of the app opens the panel address (`SYS-15`).
- Not verified: the Chrome extension on the owner's browser, and the phone and Vercel part of the manual test.

## Several projects (second step)
The panel now lists more than one project. The owner picks a folder once, gives a name and a port, and the panel lists and starts the project. Grid stays the first, built-in record. Its agent, port `3000`, plist and log do not change. Other projects are only on `127.0.0.1`. Phone and LAN access are out of scope.

| Part | Rule |
|---|---|
| Registry | `~/grid-dev-panel/projects.json`, outside the repository, mode `0600`. Each read checks every record again. A bad record is skipped and shown. |
| Folder | Only below `/Volumes/Macintosh-Data/WebDevelopment`, after `realpath`. A path part that starts with `.` is refused. The home folder is not a root. The folder dialog (`osascript`, fixed script, no arguments) opens only after a protected `POST`, one at a time. If it fails, the page shows a path field. |
| Command | The page and the API accept no command. An environment variable must be on a short allow-list (`NODE_ENV`, `NEXT_PUBLIC_*`, `VITE_*` and similar); `NODE_OPTIONS`, `PATH` and `DYLD_*` are refused. Only harmless flags pass (`--turbopack`, `--webpack`, `--mode` and similar); `--inspect`, `--config` and `--require` are refused. The panel reads `scripts.dev` from `package.json`. Only `next dev` and `vite` are known. A shell character, `&&`, a pipe or an unknown tool is refused. Expo, React Native and Metro are refused because they ask for LAN access. The panel adds `-H 127.0.0.1` (Next) or `--host 127.0.0.1` (Vite) and removes the port and host flags of the script. |
| Port | The owner gives it. The panel refuses `3030`, the port of Grid, the port of another project, and a port that `lsof` shows as in use (the holder is named). |
| Agent | One LaunchAgent for each project: `de.codelisa.dev-<slug>`, slug `[a-z0-9-]`. The panel writes the plist from a template. `ProgramArguments` is an array that runs `node <next or vite binary>` directly, with no `sh -c`. All values are XML-escaped. A project without "start at Mac login" has its plist in `~/grid-dev-panel/agents/`, so launchd does not load it at login. With the switch on, the plist is in `~/Library/LaunchAgents/`. |
| Listen check | After a start, and in every status read, the panel measures the listen address with `lsof`. A project that listens on an address other than `127.0.0.1` or `::1` is stopped with `bootout` and the card shows the reason. The check covers every listening socket of the project process tree, not only the project port, so an inspector on another port is stopped too. If `lsof` fails, the panel stops the project (fail closed). A timer of 10 seconds does the same when the page is closed. |
| Registry safety | A broken `projects.json` is never overwritten. A record that fails the check stays in the file, is shown on the page with a remove button, and its agent is stopped. One lock per registry change and one per project action stop two clicks from racing. A folder that is the same as, above or below another project (or Grid) is refused. |
| Remove | The panel stops the agent first and keeps the record if the stop fails. Only the record and the plists are deleted. Project files and the log stay. Grid cannot be removed. |
| Update | The same rule as for Grid: `git pull --ff-only` equivalent, `main`, clean tree, SHA of `origin/main`. |
| Claude | `node ~/grid-dev-panel/cli.js add <name> <port> <folder>` uses the same checks as the page. Nobody edits the JSON by hand. |

Why only Next and Vite: Next 16 in dev mode accepts a foreign `Host` header (DNS rebinding), so the loopback bind must hold, and the panel must measure it. A tool that the panel cannot bind to loopback is refused instead of started.

Verification of this step:
- 36 Node tests (`node --test test/guard.test.js test/projects.test.js`). The 17 old tests still pass. New tests: add, port conflicts (project, Grid, panel, busy port), no `dev` script, Expo and compound commands, folder outside the root, hidden folder, symlink out of the root, plist escaping, registry mode, bad records, start with a busy port, switch place of the plist, remove, loopback stop, and for each new `POST` route: no token, wrong `Origin`, foreign `Host`, cross-site, wrong token (all `403`, no `launchctl` call).
- Live with a small test project in a temporary folder: add, start, `HTTP 200` on the port, `lsof` shows `127.0.0.1` only, stop (connection refused), remove. A second test project that binds `0.0.0.0` was stopped by the panel. A third test project that also opened a listener on another port (like a Node inspector) was stopped as well with the message "this project was open to the network". The agents are gone after the test.
- Not verified: the folder dialog from the LaunchAgent session (it needs a click of the owner; the path field is the fallback), and real projects of the owner (not started by order).
